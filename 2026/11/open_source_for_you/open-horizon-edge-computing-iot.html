Open Horizon: Enabling Efficient Edge Computing for IoT

Discover why Open Horizon is so useful for IoT edge computing, check its features, learn how to install it, and build, deploy and interact with your first Open Horizon service.

By Dr R. Anand

Open Source For You  |  November 2026  |  Pages 64–68

Open Horizon is an open source platform that deploys and manages containerised applications and machine learning models on thousands of edge devices automatically. A project of LF Edge, the Linux Foundation umbrella for edge computing, it began as IBM’s Edge Application Manager before IBM contributed the code to open source.

Edge computing moves processing from a distant cloud data centre to the place where data is produced: a factory gateway, a smart camera, a retail kiosk or a Raspberry Pi in a field. For the Internet of Things (IoT), this cuts latency, saves bandwidth and keeps sensitive data local. The hard part is not running one container on one device — it is keeping the right version of the right software running on 10,000 devices that sit behind firewalls, lose connectivity and have no onsite administrator.

Open Horizon solves that problem. A central management hub stores the services you publish and the rules for where they belong. A small agent on each edge device negotiates with the hub, downloads the containers it should run, starts them and keeps them healthy, even when the network drops.

Why Open Horizon?

Open Horizon is worth choosing when you must run software on many edge devices that you cannot log into one by one. Managing an IoT fleet by hand, with SSH scripts or a cron job per device, breaks down quickly for four reasons.

  • Scale: Updating 5,000 gateways manually takes days and leaves some devices on old versions. Open Horizon pushes one change to every matching device automatically.
  • Unreliable networks: Edge devices go offline. The Open Horizon agent works autonomously, keeps services running without the hub, and catches up when the link returns.
  • Heterogeneous hardware: A fleet mixes x86 servers, ARM boards and Kubernetes clusters. Open Horizon publishes one service per architecture and lets each node pick the version that fits.
  • No onsite staff: Devices in remote places need self-healing. The agent restarts failed containers and can roll back a bad update.

Compared with sending every reading to the cloud, processing at the edge with Open Horizon lowers latency, cuts data transfer costs and keeps private data on the device. Compared with commercial edge platforms, it is free, vendor-neutral and governed openly under LF Edge, so there is no lock-in.

Key components of Open Horizon

Component Where it runs What it does
Exchange Management hub Stores users, organisations, nodes, services, policies and patterns; exposed as a REST API on port 3090
Agreement bot (agbot) Management hub Finds nodes that match a deployment policy and proposes agreements to them
Cloud Sync Service (CSS) Management hub Distributes files and machine learning models to edge nodes (port 9443)
Agent (anax) Each edge device or cluster Accepts agreements, pulls containers, runs and monitors them
hzn CLI Any admin or developer machine Command-line tool for publishing, registering and monitoring

Open Horizon combines a central control plane with autonomous edge agents. Its key features are:

  • Policy-based deployment: Nodes advertise properties such as hasCamera=true or location=factory-3. Deployment policies state constraints, and the agbot matches them automatically, so a new device that meets the rules receives its workload without any manual step.
  • Patterns: For simple fleets, a pattern names a fixed list of services that a node runs when registered with it.
  • Autonomous agents: Each agent negotiates, deploys and heals its own workloads and keeps running when disconnected from the hub.
  • Model management system: Machine learning models and configuration files are updated separately from the container that uses them, so you can retrain a model without rebuilding the service.
  • Edge devices and edge clusters: The same hub manages Docker-based devices and Kubernetes clusters such as K3s, MicroK8s and Red Hat OpenShift.
  • Security: Service definitions can be cryptographically signed, agreements are encrypted, multi-tenancy isolates organisations, and a secrets manager delivers credentials to services at run time.
  • Rollback and agent upgrades: Services can fall back to a previous version if an update fails, and node management policies upgrade the agents themselves.
  • Zero-touch onboarding: FIDO Device Onboard (FDO) support lets new devices register when first powered on.

Prerequisites for Installing Open Horizon

The simplest setup is the all-in-one install, which puts the management hub, an agent and the CLI on one machine. You need the following before you start:

Item Requirement
Operating system Ubuntu 24 on an x86_64 machine for the all-in-one hub; edge agents also run on ARM boards such as Raspberry Pi
Access A root account or sudo rights
Memory and disk At least 4GB RAM and 20GB free disk is a practical minimum for the hub (suggested, not an official figure)
Container engine Docker (installed by the script if missing); Podman works if you set DOCKER_ENGINE=podman
Tools curl, git, jq and make
Network Internet access to download images, and a fixed IP address that edge devices can reach
Open ports on the hub 3090 (Exchange), 3111 (agbot), 9443 (CSS)
Accounts A Docker Hub (or other registry) account to push your own service images

Decide on the hub’s network-facing IP address before installing. The script binds the hub to HZN_LISTEN_IP; if you skip this, only the hub machine can connect.

Installing Java and setting up the environment

Open Horizon itself does not need Java on the host. The agent and the hzn CLI are written in Go, and the Exchange, which runs on the Java Virtual Machine, ships inside its own container. Install a Java Development Kit (JDK) only if you plan to write your edge services in Java or Spring Boot.

Step 1: Update the system and install base tools

sudo apt update && sudo apt -y upgrade
sudo apt install -y curl git jq make

Step 2: Install Java (optional, for Java-based services)

sudo apt install -y openjdk-21-jdk
java -version
echo 'export JAVA_HOME=/usr/lib/jvm/java-21-openjdk-amd64' >> ~/.bashrc

Step 3: Install Docker and allow your user to run it

curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
newgrp docker
docker run hello-world

Step 4: Set the hub’s listen address

Replace the example address with your machine’s LAN IP, which you can find with hostname -I.

export HZN_LISTEN_IP=192.168.1.50

Installing Open Horizon

One script installs the whole all-in-one environment: the management hub services, the agent and the hzn CLI. Run it as root with your environment variables preserved:

sudo -E bash -c "curl -sSL https://raw.githubusercontent.com/open-horizon/devops/master/mgmt-hub/deploy-mgmt-hub.sh | bash"

The script takes several minutes. It downloads the hub images, starts the Exchange, agbot, CSS, PostgreSQL and MongoDB containers, creates an organisation called myorg with an admin user, publishes the example services, installs the agent and registers the machine as node node1. It ends by printing two credentials that you must save:

export HZN_ORG_ID=myorg
export HZN_EXCHANGE_USER_AUTH=admin:<generated-password>

Useful script options are:

FlagEffect
-AInstall the hub and CLI only, without the local agent
-ESkip loading the example services, policies and patterns
-SStop the hub services and agent
-sStart them again without reinstalling
-PPurge: delete volumes and images and uninstall the agent

Installing an agent on another device: On a separate edge device such as a Raspberry Pi, point the agent at your hub and run agent-install.sh:

export HZN_ORG_ID=myorg
export HZN_EXCHANGE_USER_AUTH=admin:<password>
export HZN_EXCHANGE_URL=http://192.168.1.50:3090/v1
export HZN_FSS_CSSURL=http://192.168.1.50:9443/
export HZN_AGBOT_URL=http://192.168.1.50:3111
export HZN_DEVICE_ID=pi-node-01
export HZN_DEVICE_TOKEN=<any-random-string>
curl -sSL https://github.com/open-horizon/anax/releases/latest/download/agent-install.sh \
| sudo -s -E bash -s -- -i css: -p IBM/pattern-ibm.helloworld -w '*' -T 120

This installs the agent from the hub’s CSS and registers the device with the sample ‘hello-world’ pattern.

Setting up Open Horizon

Set up means making your credentials permanent and confirming that the hub, the agent and the CLI can talk to each other.

Step 1 – Save the credentials

Add the two lines printed by the installer to ~/.bashrc so every new terminal has them:

echo 'export HZN_ORG_ID=myorg' >> ~/.bashrc
echo 'export HZN_EXCHANGE_USER_AUTH=admin:<generated-password>' >> ~/.bashrc
source ~/.bashrc

Step 2 – Check the installation

Each command below should return without errors.

CommandExpected result
hzn versionMatching CLI and agent versions
hzn exchange statusExchange version and health details in JSON
hzn exchange user listThe admin user of myorg
hzn node listThis node, with configstate = configured
hzn exchange service list IBM/*The example services published by the installer
docker psRunning hub containers (exchange, agbot, css, postgres, mongo) and the ‘hello-world’ service

Step 3 – Create your own user (optional)

Working as an admin is fine for learning. In a team, create a named user and an organisation for each tenant:

hzn exchange user create -o myorg -A student1 <password> student1@example.com
hzn exchange user list -o myorg student1

If hzn exchange status fails, check that the hub containers are running with docker ps and that HZN_EXCHANGE_URL points to the correct IP address and port 3090.

Create your first Open Horizon service

An Open Horizon service is an ordinary Docker container plus a JSON service definition that tells the hub its name, version, architecture and image. This example builds temp-sensor, a small IoT service that reports a simulated temperature every 5 seconds.

Step 1 — Prepare signing keys and registry login

Services are signed so that agents can verify them.

hzn key create myorg student1@example.com    # creates
# ~/.hzn/keys/service.private.key and service.public.pem
export DOCKER_HUB_ID=<your-docker-hub-id>
docker login
mkdir ~/temp-sensor && cd ~/temp-sensor

Step 2 — Write the application

Save as service.sh:

#!/bin/sh
# Simulated IoT temperature sensor
while true; do
  TEMP=$(awk -v r=$RANDOM 'BEGIN{printf "%.1f", 20 + (r % 100) / 10}')
  echo "$(date -u +%FT%TZ) node=${HZN_DEVICE_ID} temperature=${TEMP}C"
  sleep 5
done

The agent passes environment variables such as HZN_DEVICE_ID into every container, so the service can identify the device it runs on.

Step 3 — Write the Dockerfile

FROM alpine:3.20
COPY service.sh /service.sh
RUN chmod +x /service.sh
CMD ["/service.sh"]

Step 4 — Build, test locally, and push the image

docker build -t $DOCKER_HUB_ID/temp-sensor_amd64:1.0.0 .
docker run --rm -e HZN_DEVICE_ID=test $DOCKER_HUB_ID/temp-sensor_amd64:1.0.0   # Ctrl+C to stop
docker push $DOCKER_HUB_ID/temp-sensor_amd64:1.0.0

For a Raspberry Pi, build a second image tagged _arm64 with docker buildx build --platform linux/arm64.

Step 5 — Write the service definition

Save as service.definition.json, replacing <your-docker-hub-id>:

{
  "org": "myorg",
  "label": "temp-sensor for amd64",
  "url": "temp-sensor",
  "version": "1.0.0",
  "arch": "amd64",
  "public": true,
  "sharable": "singleton",
  "requiredServices": [],
  "userInput": [],
  "deployment": {
    "services": {
      "temp-sensor": {
        "image": "<your-docker-hub-id>/temp-sensor_amd64:1.0.0",
        "privileged": false
      }
    }
  }
}

For larger projects, hzn dev service generates this folder structure, a Makefile and a horizon/directory of definitions automatically, and hzn dev service start runs the service in a local simulated agent before you publish it.

Deploying the Open Horizon service

Deployment has three parts: publish the service to the Exchange, publish a deployment policy that says which nodes should run it, and give the node matching properties. The agbot then does the rest.

Publish the service: The CLI signs the definition with your key and stores it in the Exchange.

hzn exchange service publish -f service.definition.json
hzn exchange service list myorg/

Write the deployment policy: Save as deployment.policy.json. The constraint says ‘deploy to any node whose sensor property equals temperature’.

{
  "label": "Temperature sensor deployment",
  "service": {
    "name": "temp-sensor",
    "org": "myorg",
    "arch": "*",
    "serviceVersions": [ { "version": "1.0.0" } ]
  },
  "properties": [],
  "constraints": [ "sensor == temperature" ]
}

Publish the deployment policy:

hzn exchange deployment addpolicy -f deployment.policy.json temp-sensor-policy
hzn exchange deployment listpolicy

Write the node policy: Save as node.policy.json on the edge device:

{
  "properties": [ { "name": "sensor", "value": "temperature" } ],
  "constraints": []
}

Register the node with the policy: The all-in-one node is already running the sample ‘hello-world’ pattern, so unregister it first.

hzn unregister -f
hzn register --policy node.policy.json

Wait for the agreement: Within about a minute, the agbot notices that the node’s properties satisfy the policy’s constraint, proposes an agreement, and the agent pulls and starts the container.

watch hzn agreement list

The same policy now applies to every future node. Any new device registered with sensor=temperature receives temp-sensor automatically, with no further commands on the hub.

Interaction with the service

Once the service runs, you interact with it and with the fleet through the hzn CLI on the edge node and on the hub.

View the service output: The agent forwards container logs, so you see the simulated readings:

hzn service log -f temp-sensor

# 2026-10-05T09:14:05Z node=node1 temperature=24.7C
# 2026-10-05T09:14:10Z node=node1 temperature=21.3C

Common commands are:

TaskCommand
Show this node’s state and policyhzn node list and hzn policy list
See active agreementshzn agreement list
See running serviceshzn service list or docker ps
Read the agent’s event loghzn eventlog list
List all nodes in the organisation (hub)hzn exchange node list
Check why a policy does or does not matchhzn deploycheck all -b myorg/temp-sensor-policy
Remove the workload and leave the hubhzn unregister -f

Update the service: To roll out version 1.0.1, build and push the new image, change version in service.definition.json, publish it, and add { "version": "1.0.1" } to the policy’s serviceVersions. Every matching node upgrades itself. Listing the older version as well allows the agent to roll back if the new one fails.

Change behaviour with properties: Removing the property with hzn policy update on a node makes the agbot cancel the agreement and stop the container on that node only. This is how a single device is taken out of a rollout without touching the others.

Open Horizon turns the hard problem of running IoT software on thousands of unattended devices into a declarative one: you publish a service and a policy once, and autonomous agents place, run, update and heal the workloads on every matching device. In this walkthrough, one script installed a complete management hub, agent and CLI on an Ubuntu machine. A simulated temperature-sensor container was then built, signed, published and deployed through a policy, and monitored with the hzn CLI.

Because it is open source and governed by LF Edge, Open Horizon offers enterprise-grade capabilities without vendor lock-in. These include policy-based placement, separate machine learning model delivery, edge-cluster support, signed services and zero-touch onboarding. Natural next steps are to add a Raspberry Pi as a second node, deliver a machine learning model through the Model Management System, and connect the sensor output to a message broker such as MQTT or Kafka for cloud analytics.
