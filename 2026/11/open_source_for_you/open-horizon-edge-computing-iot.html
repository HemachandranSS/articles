Open Horizon: Enabling Efficient Edge Computing for IoT

Discover why Open Horizon is so useful for IoT edge computing, check its features, learn how to install it, and build, deploy and interact with your first Open Horizon service.

By Dr R. Anand

Open Source For You  |  November 2026  |  Pages 64–68

Open Horizon is an open-source platform that deploys and manages containerised applications and machine learning models on edge devices. It began as IBM’s Edge Application Manager and was contributed to LF Edge (Linux Foundation). Edge computing moves processing to where data is produced—gateways, smart cameras, retail kiosks—but managing software on thousands of devices behind firewalls, without onsite administrators, is hard.

Open Horizon’s answer is a central management hub that stores services and rules, plus a small agent on each edge device that negotiates with the hub to download and maintain containers.

Why Open Horizon?

  1. Scale — automate updates for thousands of gateways at once instead of days of manual work.
  2. Unreliable networks — the agent keeps services running offline and syncs when the link returns.
  3. Heterogeneous hardware — mixed fleets (x86, ARM, Kubernetes clusters) each pull the service variant that fits.
  4. No onsite staff — self-healing restarts failed containers or rolls back bad updates.

Edge processing also cuts latency versus shipping all data to the cloud, can reduce bandwidth cost, and helps keep sensitive data local. Governance under LF Edge keeps the project vendor-neutral.

Table 1: Key components

Component Where it runs What it does
Exchange Management hub Stores users, orgs, nodes, services, policies, patterns; REST API on port 3090
Agreement bot (agbot) Management hub Finds nodes matching a deployment policy and proposes agreements
Cloud Sync Service (CSS) Management hub Distributes files and ML models to edge nodes (port 9443)
Agent (anax) Each edge device/cluster Accepts agreements, pulls containers, runs and monitors them
hzn CLI Admin/developer machine Publish, register and monitor from the command line

Key features

  • Policy-based deployment — nodes advertise properties (e.g. hasCamera=true).
  • Patterns — fixed service lists for simple fleets.
  • Autonomous agents — negotiate, deploy and heal independently.
  • Model management — update ML models separately from containers.
  • Devices and clusters — Docker and Kubernetes (K3s, MicroK8s, OpenShift).
  • Security — signed service definitions, encrypted agreements, secrets management.
  • Rollback and agent upgrades — fall back service versions; node management policies upgrade agents.
  • Zero-touch onboarding — FIDO Device Onboard (FDO) support.

Installing Open Horizon

Set the hub listen address first (hostname -I for your LAN IP):

export HZN_LISTEN_IP=192.168.1.50
sudo apt update && sudo apt -y upgrade
sudo apt install -y curl git jq make
# optional for Java services:
sudo apt install -y openjdk-21-jdk
curl -fsSL https://get.docker.com | sh
sudo usermod -aG docker $USER
newgrp docker

All-in-one hub + agent + CLI (as root):

sudo -E bash -c "curl -sSL https://raw.githubusercontent.com/open-horizon/devops/master/mgmt-hub/deploy-mgmt-hub.sh | bash"
export HZN_ORG_ID=myorg
export HZN_EXCHANGE_USER_AUTH=admin:<generated-password>
FlagEffect
-AHub and CLI only (no local agent)
-ESkip example services/policies/patterns
-S / -sStop / start hub services and agent
-PPurge volumes, images and uninstall agent

On a separate device (e.g. Raspberry Pi), point the agent at the hub with HZN_EXCHANGE_URL, HZN_FSS_CSSURL, HZN_AGBOT_URL, device ID/token, then run agent-install.sh. Persist credentials in ~/.bashrc and verify with hzn version, hzn exchange status, hzn node list and docker ps.

Create your first service: temp-sensor

A small service that prints a simulated temperature every five seconds.

hzn key create myorg student1@example.com
export DOCKER_HUB_ID=<your-docker-hub-id>
docker login
mkdir ~/temp-sensor && cd ~/temp-sensor

service.sh (simulated sensor), Alpine Dockerfile, then:

docker build -t $DOCKER_HUB_ID/temp-sensor_amd64:1.0.0 .
docker run --rm -e HZN_DEVICE_ID=test $DOCKER_HUB_ID/temp-sensor_amd64:1.0.0
docker push $DOCKER_HUB_ID/temp-sensor_amd64:1.0.0
# ARM: docker buildx build --platform linux/arm64 ...

Publish a service.definition.json (org myorg, url temp-sensor, version 1.0.0, arch amd64), then:

hzn exchange service publish -f service.definition.json
hzn exchange service list myorg/

Add a deployment policy that constrains on sensor == temperature, a node policy advertising sensor=temperature, then:

hzn exchange deployment addpolicy -f deployment.policy.json temp-sensor-policy
hzn unregister -f
hzn register --policy node.policy.json
watch hzn agreement list
hzn service log -f temp-sensor
# e.g. 2026-10-05T09:14:05Z node=node1 temperature=24.7C

Updates and next steps

Roll out version 1.0.1 by bumping service.definition.json and adding it to the policy’s serviceVersions. Changing node properties (e.g. removing a matching property with hzn policy update) lets the agbot stop the container on that node alone.

Open Horizon is built for thousands of unattended devices, open source under LF Edge. Natural next steps: add a Raspberry Pi as a second node, or use the Model Management System (MMS) to push ML models independently of containers.
