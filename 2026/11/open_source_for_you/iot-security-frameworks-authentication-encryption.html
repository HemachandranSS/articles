IoT Security Frameworks: Facilitating Device Authentication and Data Encryption

Open source IoT security frameworks are great at identifying devices and keeping the conversation between them private. It helps that their code is public and free to use.

By Dr Geetali Saha and Kush Patel

Open Source For You  |  November 2026  |  Pages 60–63

Internet of Things devices are everywhere: smart meters, factory sensors, cameras, door locks and wearables. Most are small, cheap and expected to run for years without anyone touching them. That combination makes them attractive targets. A single device with a default password or an unencrypted connection can give an attacker a way into an entire network.

Two questions sit at the centre of IoT security. First, who is this device really talking to, and is it who it claims to be? That is authentication. Second, even if the right parties are talking, can anyone else read or change what they say? That is encryption and integrity protection. Writing your own cryptography is a bad idea, so teams reuse existing open-source code—public, reviewed and free—but incorrect setup can still make them unsafe.

Security foundations for IoT

The NIST baseline for IoT devices lists six core capabilities: device identification, device configuration, data protection, logical access to interfaces, software update, and cybersecurity state awareness. Authentication and encryption map directly onto these mechanisms. Figure 1 uses a simple three-layer view—device, network, and cloud/edge—throughout the article.

Table 1: Security goals and open-source mechanisms

Goal Meaning Open-source support
Authentication Prove who a device or server is X.509 certificates, pre-shared keys, mutual TLS
Confidentiality Keep data unreadable to outsiders TLS 1.3, DTLS 1.3, AES-GCM
Integrity Detect tampering Authenticated encryption, digital signatures
Trusted firmware Run only approved code Signed images and secure boot (MCUBoot)
Key management Store and rotate secrets safely Secret store in EdgeX, hardware key storage

A layered view of IoT security

  • Device layer — secure boot (MCUBoot), Mbed TLS / wolfSSL, key storage: prove identity; protect keys and firmware.
  • Network layer — TLS 1.3 (TCP), DTLS 1.3 (UDP), MQTT / CoAP / LwM2M: encrypt and authenticate every connection.
  • Cloud / edge layer — Mosquitto broker, EdgeX Foundry, PKI and secret store: authorise devices, store keys, process data.

Device authentication

Pre-shared keys (PSK) are simple but hard to manage at scale. Certificate-based authentication with X.509 certificates and mutual TLS (mTLS) scales better. Libraries such as Mbed TLS and brokers such as Eclipse Mosquitto make this practical.

Figure 2 summarises a simplified mutual TLS 1.3 handshake: ClientHello → ServerHello with server certificate and request for client certificate → device certificate plus proof of private key → Finished messages → encrypted MQTT/CoAP application data. Both sides then know who the other is, and further traffic stays encrypted.

Listing 1: Mosquitto requiring client certificates

listener 8883
cafile /etc/mosquitto/certs/ca.crt
certfile /etc/mosquitto/certs/server.crt
keyfile /etc/mosquitto/certs/server.key
require_certificate true
use_identity_as_username true
allow_anonymous false

Table 2: Common authentication methods

Method Idea Trade-off
Pre-shared key Same secret on both sides Small/fast; hard to manage at scale
X.509 certificate CA-signed identity Strong unique identity; needs PKI
Raw public key Public key known in advance No CA; manual key distribution
Token (JWT, OAuth) Short-lived signed token Easy to expire; needs token service
Hardware-backed key Private key in secure chip Cannot be copied; adds hardware cost

Data encryption

Protect data in transit with TLS 1.3, DTLS 1.3 or OSCORE, and protect data at rest as well. Prefer authenticated encryption and never store secrets in plain text.

Table 3: Encryption building blocks

Primitive Role Best suited for
AES-GCM Authenticated encryption Chips with AES hardware acceleration
ChaCha20-Poly1305 Authenticated encryption Small CPUs without AES hardware
ECDHE (P-256, X25519) Key agreement per session Forward secrecy on constrained devices
ECDSA, Ed25519 Digital signatures Certificates and firmware signing
Ascon Lightweight authenticated encryption Very small devices (NIST selection, 2023)

Open source frameworks compared

Frameworks fall into cryptographic libraries (building blocks) and full platforms. Licence choice matters (Apache 2.0 vs GPL), and secure boot ties firmware trust to the rest of the stack.

Table 4: Cryptographic and TLS libraries

Library Licence Strength Typical use
Mbed TLS Apache-2.0 or GPL-2.0-or-later Small, readable code Microcontrollers, Zephyr
wolfSSL GPLv3 or commercial Compact, many ports Embedded and RTOS devices
OpenSSL Apache-2.0 (v3+) Feature-rich, widely tested Gateways, Linux devices
libsodium ISC Simple, hard-to-misuse API Custom protocols, apps

Table 5: Platforms and tools

Framework Role Security features
Eclipse Mosquitto MQTT broker TLS, client certificates, ACLs
EdgeX Foundry Edge computing platform Secret store and API gateway
MCUBoot Secure bootloader Signed images, rollback protection, safe updates
Zephyr RTOS Real-time OS Integrates TLS libraries and MCUBoot
Eclipse Leshan LwM2M device management DTLS with PSK, raw public key or certificates

Practical guidance

  • Give every device unique credentials.
  • Never switch off certificate checking.
  • Keep cryptographic libraries updated.
  • Plan for signed firmware updates from day one.

A strong starter project is a device that connects to a Mosquitto broker with mutual TLS—using Mbed TLS or OpenSSL on the device side, Mosquitto for certificate checks, and MCUBoot / EdgeX for firmware and secret protection.

Limitations

Open source is not a magic fix. Constrained memory and power make cryptography expensive; key provisioning and revocation are operationally hard; physical attacks remain real; and post-quantum migration is coming. Still, public frameworks let teams identify devices and keep conversations private—if they are configured carefully.
