IoT Security Frameworks: Facilitating Device Authentication and Data Encryption

Open source IoT security frameworks are great at identifying devices and keeping the conversation between them private. It helps that their code is public and free to use.

By Dr Geetali Saha and Kush Patel

Open Source For You  |  November 2026  |  Pages 60–63

Internet of Things (IoT) devices are everywhere: smart meters, factory sensors, cameras, door locks and wearables. Most of them are small, cheap and expected to run for years without anyone touching them. That combination makes them attractive targets. A single device with a default password or an unencrypted connection can give an attacker a way into an entire network.

Two questions sit at the heart of IoT security. First, who is this device really talking to, and is it who it claims to be? That is authentication. Second, even if the right parties are talking, can anyone else read or change what they say? That is encryption and integrity protection. A good design answers both, from the moment the device boots to the moment its data reaches the cloud. Writing your own cryptography is a famously bad idea, so teams usually reuse existing code. Open source frameworks are popular for this because their code is public, widely reviewed, free to use and not tied to one vendor. They still need correct setup, though, and a well-known library used badly is not safe.

Security foundations for IoT

A useful starting point is the NIST baseline for IoT devices, which lists six core capabilities a device should have: device identification, device configuration, data protection, logical access to interfaces, software update, and cybersecurity state awareness. Authentication and encryption sit mainly under the first, third and fourth of these. Table 1 shows how common security goals map to open source mechanisms.

Security works best in layers, so that a failure in one place does not expose everything. Figure 1 shows a simple three-layer view that we will use throughout this document.

Table 1: Security goals and the open source mechanisms that support them

Security goal What it means Typical open source mechanism
Authentication Prove who a device or server is X.509 certificates, pre-shared keys, mutual TLS
Confidentiality Keep data unreadable to outsiders TLS 1.3, DTLS 1.3, AES-GCM
Integrity Detect any tampering with data Authenticated encryption, digital signatures
Trusted firmware Run only approved code Signed images and secure boot (MCUboot)
Key management Store and rotate secrets safely Secret store in EdgeX, hardware key storage

Figure 1: A layered view of IoT security — Cloud / edge (Mosquitto broker, EdgeX Foundry, PKI and secret store: authorise devices, store keys, process data); Network (TLS 1.3 for TCP, DTLS 1.3 for UDP, MQTT / CoAP / LwM2M: encrypt and authenticate every connection); Device (secure boot with MCUboot, Mbed TLS / wolfSSL, key storage: prove identity, protect keys and firmware).

Device authentication

Authentication gives every device an identity that cannot easily be copied. The simplest method is a pre-shared key (PSK), where the device and server hold the same secret. It is light on memory and processing power, but if one device is cracked, its key is exposed, and managing thousands of shared secrets gets messy fast.

The stronger and more common approach is certificate-based authentication. Each device gets its own private key and an X.509 certificate signed by a trusted certificate authority (CA). In mutual TLS, the server proves itself to the device and the device proves itself to the server, as sketched in Figure 2. Libraries such as Mbed TLS support this on very small devices. Table 2 compares the main options.

In practice, a message broker is the easiest place to enforce this. Eclipse Mosquitto, a popular open source MQTT broker, can be told to refuse any client that does not present a valid certificate. Listing 1 shows a short configuration that does exactly that.

Figure 2: Simplified mutual TLS 1.3 handshake between an IoT device (client) and a broker (server): ClientHello (supported ciphers, key share) → ServerHello, server certificate, request for client certificate → Device certificate + proof of private key, Finished → Server Finished; session keys agreed → Encrypted application data (MQTT / CoAP). Both sides now know who the other is, and all further traffic is encrypted.

Listing 1: Mosquitto configuration requiring client certificates

listener 8883
cafile /etc/mosquitto/certs/ca.crt
certfile /etc/mosquitto/certs/server.crt
keyfile /etc/mosquitto/certs/server.key
require_certificate true
use_identity_as_username true
allow_anonymous false

With these lines, the broker listens only on the encrypted port, rejects anonymous clients, and uses the name inside each device certificate as its username, so access rules can be written per device. The private key for each device should ideally live in a secure element or protected memory rather than in plain flash storage.

Table 2: Common authentication methods for IoT devices

Method How it works Strength Weakness
Pre-shared key Same secret stored on both sides Small and fast Hard to manage; one leak is costly
X.509 certificate CA-signed identity per device Strong, unique identity Needs PKI and revocation
Raw public key Public key known in advance No CA needed; lightweight Manual key distribution
Token (JWT, OAuth) Short-lived signed token Easy to expire and revoke Needs a trusted token service
Hardware-backed key Private key kept in a secure chip Key cannot be copied out Extra hardware cost

Data encryption

Encryption protects data in transit (moving across a network) and at rest (stored on a device or server). For data in transit, TLS 1.3 is the current standard for TCP connections, and it removed many older, weaker options. For devices that use UDP, such as those running CoAP, DTLS 1.3 offers the same protection and was designed with constrained devices in mind. Where messages pass through several hops, object-level protection such as OSCORE can keep them encrypted from device to final receiver.

Most modern protocols rely on authenticated encryption, which hides the data and detects tampering in a single step. Table 3 lists the main building blocks and where they fit.

For data at rest, the main rule is simple: never leave secrets in plain text. Keys and credentials belong in a protected store, such as the secret store included with EdgeX Foundry or the secure storage offered by the chip itself. Encrypting sensitive files on flash adds another layer if a device is stolen or its memory is read out.

Table 3: Encryption building blocks used in open source IoT stacks

Primitive Role Best suited for
AES-GCM Authenticated encryption Chips with AES hardware acceleration
ChaCha20-Poly1305 Authenticated encryption Small CPUs without AES hardware
ECDHE (P-256, X25519) Key agreement per session Forward secrecy on constrained devices
ECDSA, Ed25519 Digital signatures Certificates and firmware signing
Ascon Lightweight authenticated encryption Very small devices (selected by NIST in 2023)

Open source frameworks compared

The frameworks fall into two groups. Cryptographic libraries provide the building blocks, such as TLS, ciphers and certificates. Platforms and tools use those libraries to deliver complete features such as secure messaging, device management and secure updates. Table 4 compares four widely used libraries.

The licence matters more than it might seem. A permissive licence such as Apache 2.0 lets a company ship a product without opening its own code, while the GPL does not. Teams should check this early, before they build around a library.

Beyond libraries, several platforms bring everything together. Table 5 summarises five of them, and Figure 3 shows one of the most important protections, Secure Boot, which stops a device from running firmware that has not been properly signed.

Practical guidance

Choosing a framework is only half the job. Most real-world breaches come from avoidable mistakes, not broken cryptography. A few habits help a great deal. Give every device its own unique credentials instead of one shared key baked into the firmware. Never switch off certificate checking just to make a test work and then forget to switch it back on. Keep the libraries updated, because TLS code is a frequent target for vulnerabilities. Finally, plan for firmware updates from day one, since a device that cannot be patched will eventually become a liability.

It also helps to match the tools to the device. A tiny sensor with a few hundred kilobytes of memory may pair Zephyr with Mbed TLS and MCUboot, while a Linux gateway can run OpenSSL and Mosquitto comfortably. Starting from the NIST capabilities and checking each one against the design is a good way to avoid gaps.

Limitations and challenges

Open source is not a magic fix. Constrained devices have little memory and power, so heavy cryptography can drain batteries or slow responses. Provisioning keys and certificates to thousands of devices securely, and revoking them when something goes wrong, is difficult and often underestimated. Physical attacks and side channels can leak keys from unprotected hardware. Looking ahead, future quantum computers may weaken today’s public-key algorithms, so long-lived devices should be built with the ability to upgrade their cryptography. Last, open source projects depend on maintainers, so it pays to choose actively supported ones.

Securing IoT devices comes down to knowing who is talking and keeping their conversation private. Open source frameworks make both achievable: libraries like Mbed TLS and OpenSSL supply TLS and DTLS, brokers like Mosquitto enforce certificate checks, and tools like MCUboot and EdgeX protect firmware and secrets. The best results come from combining them in layers, configuring them carefully and keeping them up to date. For a student or developer starting out, a good first project is a small device that connects to a Mosquitto broker using mutual TLS, because it covers identity, encryption and key handling in one go.
