Building an Open Source Edge AI Platform: From Device to Distributed Intelligence

Scaling edge AI devices comes with a host of challenges. The job must be done correctly and with caution.

By Vishal Tanna

Open Source For You  |  November 2026  |  Pages 69–72

A manufacturing client showed me a defect detection system in March this year. Camera over the line, a Jetson board running a vision model, bounding boxes drawn in real time. It worked beautifully.

Then they mentioned the plan was forty-two plants! That is where the conversation changes. One edge AI device is an engineering achievement. Four thousand is a different discipline, and little of what you learned building the first one is of use.

I wrote earlier (OSFY, September 2026) that building AI features and operating them are separate problems. At the edge the gap is wider, because you lose both things that make cloud operations tractable: you cannot reach the machine, and the machine is not always online.

What changes at scale is:

Concern One device A fleet
Deployment SSH and docker run Declarative, pull-based, survives offline nodes
Model update Copy a file Versioned artefact, staged rollout, rollback path
Failure You notice Nobody notices for three weeks
Hardware Identical Three generations, two vendors, mixed accelerators
Cost Electricity Bandwidth, and it is not small

The third row is important. In a cloud service a broken deploy pages somebody in minutes. At the edge, a model that degraded because winter lighting changed at one plant keeps producing confident, wrong output until a floor supervisor eventually mentions it to IT.

The four tiers

Most working edge platforms settle into the same shape, not by mandate but because the constraints push you there.

  • Tier 1 – Device runtime: Inference engine, local buffering, health agent
  • Tier 2 – Node orchestration: K3s/KubeEdge, workload lifecycle, device discovery
  • Tier 3 – Fleet control: GitOps reconciliation, model registry, OTA pipeline
  • Tier 4 – Aggregation: Telemetry store, retraining pipeline, dashboards

Decide which tier owns each capability. Trouble starts when inference logic creeps into tier 3, or fleet policy gets baked into a container shipping to tier 1.

The dashed line in Figure 1 is the whole article. Everything below it must keep working when the link drops. Everything above must tolerate nodes that vanish for a day and return with a backlog.

Tier 1: What runs on the box

Pick your runtime by hardware, not preference.

Runtime Best fit
ONNX Runtime Mixed fleets. Broadest execution providers: CUDA, TensorRT, OpenVINO, NNAPI, CoreML
LiteRT Mobile and embedded. Successor to TensorFlow Lite, with LiteRT-LM for on-device language models
OpenVINO Intel CPUs, GPUs, NPUs. NNCF INT8 routinely gives 2x to 3x speedup
TensorRT NVIDIA Jetson. Fastest on NVIDIA silicon; least portable
llama.cpp On-device LLMs on almost anything

If your fleet is genuinely heterogeneous, which most are after two refresh cycles, ONNX Runtime is the pragmatic default. You pay in footprint and buy the ability to ship one artefact to three hardware generations.

Quantization is not optional here. INT8 typically gives a two to threefold speedup at roughly a quarter the model size, with accuracy loss often within noise for detection work. Measure on your own data but expect to ship INT8.

Two things the device tier must do beyond inference, and both are forgotten in prototypes. Buffer locally, because when the uplink drops, results need somewhere to go, with a defined policy for what happens when the buffer fills. And report health unprompted, since pull-based monitoring does not work across NAT, cellular links, or devices that sleep.

Tier 2: Orchestration without the cloud

K3s is CNCF-conformant Kubernetes in one binary, running in 512MB to 1GB for a server node and around 256MB for an agent, with ARM and x86 parity. For most sites with a reasonable box, this is the answer.

KubeEdge splits into CloudCore beside your API server and EdgeCore on edge nodes, caching state in SQLite and running workloads autonomously when the link is down. It has more moving parts than K3s, which is worth it when offline autonomy is a hard requirement.

Akri, a CNCF Sandbox project, exposes leaf devices such as IP cameras as Kubernetes resources, handling their appearance and disappearance. If your workload is fundamentally cameras, it removes a lot of glue code.

These compose. A Fleet-managed K3s cluster at a regional aggregation point can host CloudCore for devices beneath it.

On GitOps: Push-based deployment fails at the edge for the obvious reason. The pull model inverts it. Each site runs an agent that pulls desired state from Git when connectivity returns and reconciles itself. Rancher Fleet, Argo CD, and Flux all do this, and your source of truth stays a repository of plain manifests.

defaultNamespace: edge-inference
helm:
  chart: ./charts/vision-inference
  values:
    modelVersion: "2026.09.3"
    inferenceRuntime: onnxruntime
targetCustomizations:
  - name: jetson-sites
    clusterSelector:
      matchLabels: { hardware: jetson-orin }
    helm:
      values: { inferenceRuntime: tensorrt }
  - name: intel-sites
    clusterSelector:
      matchLabels: { hardware: intel-nuc }
    helm:
      values: { inferenceRuntime: openvino }

One definition — hardware overrides by label. That pattern is most of what fleet management is.

Tier 3: Models are not container images

This is the part teams get wrong most often. The instinct is to bake the model into the image. It works until about fifty devices, then fails for three reasons. Updates require a full rebuild and redeploy. A 400MB image pushed to four thousand devices over cellular is a bandwidth bill someone will query. And you lose the ability to roll back the model independently of application code, which is exactly the rollback you want at 2 am. Separate them.

registry.internal/edge-inference:1.8.2
# application, changes rarely

models.internal/defect-detect/2026.09.3.onnx
# model, changes often

The device caches the current and previous. Rollback becomes a config change completing in seconds with no network. Staged rollout is mandatory, not a refinement:

  1. canary — 5 devices, 48 hours, chosen for hardware diversity
  2. pilot — 1 site, 1 week, human validating output
  3. ring 1 — 10% of fleet
  4. ring 2 — 50%
  5. full — remainder

Design an automatic halt on an error budget at every stage. Those 48 hours matter more than they look, because edge failures are often environmental and need a full day-night cycle to surface. A model that behaves at 2 pm can fall apart under fluorescent light at 11 pm.

For base system OTA rather than workloads, Mender, RAUC and SWUpdate all use A/B partitions with automatic rollback on failed boot.

Tier 4: Seeing a fleet you cannot reach

Bandwidth shapes everything. Shipping full Prometheus scrapes from every device is not viable over metered links, so the pattern is local aggregation, push to a collector, and sample rather than complete.

Signal Frequency Why
Heartbeat with model version 1 to 5 min What is deployed is never quite what you think
Inference latency p50, p95 5 min, pre-aggregated Hardware degradation shows here first
Input distribution summary Hourly Drift detection, the most valuable edge signal
Confidence distribution Hourly A falling mean is your early warning
Resource pressure 5 min Thermal throttling is common and otherwise invisible
Full inference samples 0.1% or lower For the retraining set

OpenTelemetry handles transport, and a collector on the device with batching and retry turns an offline period into a backlog rather than a hole.

Input drift is how edge AI dies. The model is trained on one plant in one season. Camera angles shift, lighting gets replaced, a supplier changes a component colour. None of this throws an error or moves a latency metric. A statistical summary of input features compared against the training distribution catches it weeks before a human does. Evidently, NannyML works well on aggregated summaries at tier 4.

Security

The edge threat model differs in one way that matters: the attacker may have physical access.

The practical minimum is secure boot with signed images, device identity rather than shared secrets (SPIFFE and SPIRE give each device short-lived credentials, where a shared key baked into four thousand images is one stolen device away from a bad week), signed model artefacts verified with Cosign before load, mutual TLS to the control plane, and encrypted local storage for buffered data.

None of it is exotic. All of it is far easier to build in than to retrofit across a deployed fleet.

Cost is bandwidth

You already bought the compute, so the recurring number is data movement. Model distribution is large and spiky but controllable through delta updates. Telemetry is moderate and constant, and controllable through aggregation. Raw data for retraining is the one that surprises people.

That last is the trap. Someone collects training data from production, nobody sets a sampling rate, and a thousand cameras start uploading frames. Put the rate in tier 3 config, adjustable without redeploy, with an alert on aggregate egress.

Delta updates are worth the engineering. A 400MB model to four thousand devices is 1.6TB. A binary diff against the cached previous version is frequently a tenth of that.

Build order

  • Weeks 1–3: One device under GitOps control. Nothing else changes.
  • Weeks 4–6: Separate model from image. Registry, version selector, cache.
  • Weeks 7–9: Telemetry. Heartbeat, latency, drift summaries, a dashboard showing deployed model version per device.
  • Weeks 10–12: Staged rollout machinery. Test the halt by deliberately shipping a bad model to the canary.

Teams that scale first and build the platform afterwards end up doing both at once, under pressure, with devices already in the field.

Where this leaves us

The manufacturing client is at eleven plants rather than forty-two, which is slower than planned and the right call. They spent a quarter building tiers 2 and 3 against a handful of devices, and the rollout since has been uneventful.

What convinced them was not architecture. It was the first staged rollout halting automatically at canary because confidence dropped on two of five devices, both at a plant with different overhead lighting. Across forty-two sites simultaneously, it would have been weeks before anyone connected the defect reports to the deployment.

That is the case for the platform layer, and it is the same case I made in September. The hard problem stopped being the model a while ago. It is running a thousand copies of it in places you cannot reach, without losing track of what they run and whether it still works.

Every component here is open source and most run on hardware you already own. Start with one device under GitOps control. That is a weekend, and everything else builds on it.
