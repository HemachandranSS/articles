Building an Open Source Edge AI Platform: From Device to Distributed Intelligence

Scaling edge AI devices comes with a host of challenges. The job must be done correctly and with caution.

By Vishal Tanna

Open Source For You  |  November 2026  |  Pages 69–72

A manufacturing client once showed a defect-detection system: a camera and a Jetson board that worked beautifully on one line. Scaling that to forty-two plants—and thousands of devices—is a different discipline. Building AI features and operating them are separate problems; at the edge the gap is wider because you cannot always reach the machine, and the machine is not always online. (This piece continues themes from an earlier OSFY article in September 2026.)

What changes at scale

One device A fleet
Deployment SSH and docker run Declarative, pull-based, survives offline nodes
Model update Copy a file Versioned artefact, staged rollout, rollback path
Failure You notice Nobody notices for three weeks
Hardware Identical Three generations, two vendors, mixed accelerators
Cost Electricity Bandwidth—and it is not small

The four tiers

  1. Tier 1 — Device runtime: inference engine, local buffering, health agent.
  2. Tier 2 — Node orchestration: K3s / KubeEdge, workload lifecycle, device discovery.
  3. Tier 3 — Fleet control: GitOps reconciliation, model registry, OTA pipeline.
  4. Tier 4 — Aggregation: telemetry store, retraining pipeline, dashboards.

Figure 1’s dashed line is the whole article: everything below (tiers 1–2) must work when the link drops; everything above (tiers 3–4) must tolerate nodes vanishing for a day and returning with a backlog. Telemetry flows up; desired state flows down.

Tier 1: What runs on the box

Pick a runtime by hardware, not preference:

Runtime Best fit
ONNX Runtime Mixed fleets; broad execution providers (CUDA, TensorRT, …)
LiteRT Successor to TensorFlow Lite; mobile/embedded and on-device LMs
OpenVINO Intel CPU/GPU/NPU; ~2–3× with NNCF INT8
TensorRT Fastest on NVIDIA Jetson; least portable
llama.cpp On-device LLMs

Quantization (INT8) is essential for speed and size. Local buffering keeps inference alive offline and turns outages into backlogs instead of data holes.

defaultNamespace: edge-inference
helm:
  chart: ./charts/vision-inference
  values:
    modelVersion: "2026.09.3"
    inferenceRuntime: onnxruntime
targetCustomizations:
  - name: jetson-sites
    clusterSelector:
      matchLabels: { hardware: jetson-orin }
    helm:
      values: { inferenceRuntime: tensorrt }
  - name: intel-sites
    clusterSelector:
      matchLabels: { hardware: intel-nuc }
    helm:
      values: { inferenceRuntime: openvino }

Tier 2: Orchestration without the cloud

K3s is CNCF-conformant and often runs in about 512 MB–1 GB for server nodes. KubeEdge splits CloudCore (beside the API server) and EdgeCore (on the node) so workloads keep running when links die. Akri (CNCF Sandbox) exposes leaf devices such as IP cameras as Kubernetes resources. Prefer pull-based GitOps (Argo CD, Flux) so agents reconcile from Git even after offline periods.

Tier 3: Models are not container images

Baking models into images inflates bandwidth and slows redeploys. Keep them separate:

registry.internal/edge-inference:1.8.2          # application — changes rarely
models.internal/defect-detect/2026.09.3.onnx   # model — changes often

Staged rollout: canary (5 devices, 48 hours for hardware diversity) → pilot (1 site, 1 week with human validation) → ring 1 (10%) → ring 2 (50%) → full. Halt automatically on error budgets—edge models can behave differently under 2 p.m. vs 11 p.m. lighting.

Tier 4: Seeing a fleet you cannot reach

Full Prometheus scrapes over metered links are not viable. Aggregate locally, push to a collector, and sample:

Signal Frequency Why
Heartbeat with model version 1–5 min What is deployed is never quite what you think
Inference latency p50 / p95 5 min, pre-aggregated Hardware degradation shows here first
Input distribution summary Hourly Drift detection—the most valuable edge signal
Confidence distribution Hourly A falling mean is early warning
Resource pressure 5 min Thermal throttling is otherwise invisible
Full inference samples ≤ 0.1% For the retraining set

OpenTelemetry for transport, plus a device collector with batching and retry, turns offline time into a backlog. Input drift is how edge AI dies: new lighting, camera angles, supplier colours. Summaries compared to the training distribution (e.g. with Evidently or NannyML at tier 4) catch it weeks before humans do.

Security

The attacker may have physical access. Practical minimum: secure boot with signed images; per-device identity (SPIFFE/SPIRE short-lived credentials—not one key baked into four thousand images); Cosign-verified model artefacts before load; mutual TLS to the control plane; encrypted local storage for buffers. Easier to build in than retrofit.

Cost is bandwidth

Compute is already bought; the recurring bill is data movement. Model distribution is large and spiky—control it with delta updates (a 400 MB model × 4,000 devices = 1.6 TB; a diff is often ~1/10th). Telemetry is moderate if aggregated. Raw retraining frames are the trap—put sampling rate in tier-3 config with an egress alert.

Build order

  • Weeks 1–3: one device under GitOps—nothing else changes.
  • Weeks 4–6: separate model from image; registry, version selector, cache.
  • Weeks 7–9: telemetry—heartbeat, latency, drift summaries, dashboard of model version per device.
  • Weeks 10–12: staged rollout; deliberately ship a bad model to canary to test the halt.

Teams that scale first and build the platform afterwards end up doing both at once, under pressure, with devices already in the field.

Where this leaves us

The manufacturing client is at eleven plants rather than forty-two—slower than planned and the right call. A quarter spent on tiers 2–3 against a handful of devices made later rollout uneventful. What convinced them was not architecture diagrams: the first staged rollout halted at canary because confidence dropped on two of five devices at a plant with different overhead lighting. Across forty-two sites at once, defect reports would have taken weeks to connect to the deploy.

The hard problem stopped being the model a while ago. It is running a thousand copies in places you cannot reach, without losing track of what they run and whether it still works. Every component here is open source and most run on hardware you already own. Start with one device under GitOps. That is a weekend—and everything else builds on it.
