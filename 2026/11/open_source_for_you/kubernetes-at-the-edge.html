Kubernetes at the Edge: From Cloud Native to Resource-Constrained Devices

The interesting thing about Kubernetes at the edge is that it reflects a broader change in how we think about infrastructure.

By Dhaval Gajjar

Open Source For You  |  November 2026  |  Pages 50–52

A friend who runs operations for a mid-sized retail chain had a familiar problem. Two years ago, each store had a small server in a back room running point-of-sale software, inventory sync and analytics. The setup had grown organically over a decade and was a nightmare to update—physical store visits or fragile VPN scripts for every software push.

He asked whether Kubernetes could help. Stock Kubernetes would have eaten half the available memory on a store server just running itself. Then we found k3s. Over a few months it rolled out to forty stores. Deployments that once took a week shrank to about twenty minutes. This article is about that messy, resource-constrained, we-have-no-staff-at-this-site version of Kubernetes.

Why edge is a different animal

Running Kubernetes in a data centre is not the same as running it at the edge. Four factors dominate:

  1. Hardware is smaller. A typical edge node might be an industrial PC with four cores and eight GB of RAM—or less. Stock Kubernetes will not behave well if you simply drop it there.
  2. Networks are unreliable. Sites have patchy connectivity or cellular links that drop. The orchestrator must tolerate periods when the central control plane is unreachable, and local workloads must keep running.
  3. Sites are physically dispersed. With twenty to five thousand sites, manual SSH into each is impossible. Fleet management becomes critical.
  4. Staffing is thin. There are no engineers at a petrol pump or similar site. If something breaks at 2 a.m., it must self-heal—or wait until morning.

The lightweight distributions, briefly

Standard Kubernetes is too heavy for devices such as a Raspberry Pi. Common edge-friendly options:

  • K3s — certified distribution from Rancher (now SUSE); binary under ~70 MB; replaces etcd with SQLite by default; often under ~0.5 GB RAM.
  • MicroK8s — Canonical’s snap-based install on Ubuntu.
  • KubeEdge — extends Kubernetes with a cloud control plane and a lightweight EdgeCore agent on the device.
  • k0s — single-binary distribution close to upstream Kubernetes.

Rule of thumb: use K3s for self-contained clusters at each site; use KubeEdge when you want one logical cluster spanning cloud and edge.

Getting K3s running on a small device

curl -sfL https://get.k3s.io | sh -
sudo k3s kubectl get nodes
sudo k3s kubectl get pods -A

Add a worker:

curl -sfL https://get.k3s.io | K3S_URL=https://main-server:6443 K3S_TOKEN=mynodetoken sh -

Designing for intermittent connectivity

  • Local autonomy — each site runs its own cluster (classic K3s pattern).
  • Hybrid control plane — cloud control plane with local state caching (KubeEdge pattern).
  • GitOps-driven sync — Flux or Argo CD pull config from Git so a site can keep running on the last known good state if Git is unreachable.

Workload patterns that fit the edge

Good for the edge: latency-sensitive processing (industrial control, real-time analytics); bandwidth-sensitive filtering (shrink 1 GB/hr of raw data to ~10 MB of signal); resilience-critical services that must run offline (petrol pumps, hospital admissions); compliance and data residency where data cannot leave the site.

Better in the cloud: analytics dashboards, model training, long-term storage.

Fleet management, the real daily problem

Rancher is a heavyweight choice for managing many K3s clusters—UI, policy and access control. Fleet (from Rancher) targets GitOps across many clusters, grouping them by labels. Argo CD scales via ApplicationSets that template deployments across clusters. Akri exposes IoT devices as Kubernetes resources pods can discover—useful when workloads and physical devices share a site.

For the retail chain, Rancher plus Argo CD worked well: ops got a central dashboard; developers worked with Git. Opening a new store became a two-hour provisioning job instead of a week.

Storage, networking, and the things that bite

Storage is weirder at the edge. In the cloud you have managed block and object storage; at the edge you have local disk—often slow, small and unreliable. Plan for what happens when an SD card dies.

Networking means NAT, firewalls and sites unreachable from outside. WireGuard is popular and light; Tailscale builds easier key management on top of it.

Resource contention is real—edge devices often run more than Kubernetes workloads. Set requests and limits carefully; use node labels and taints to control placement. Updates are a project at scale: staged rollouts and a canary site first, not a fleet-wide bang.

Security at the edge is different

Physical access is a real threat. Encrypt disks; use secure boot when hardware allows; assume local credentials can be extracted and limit what they grant. Authenticate and encrypt every connection—zero trust applies even more strongly. Sign images and enforce them with admission controllers so compromise of one site does not cascade. Secrets are tricky when Vault may be unreachable: cache carefully or use device HSMs.

A real-world example, condensed

After migration, each store had an Intel NUC with 8 GB of RAM running K3s and five workloads: point-of-sale backend, inventory sync agent, customer display service, a tiny Prometheus instance, and a log forwarder to the central platform.

All configuration lived in Git. Argo CD on each cluster pulled every two minutes; deployments were pull requests; developers never touched a store directly. The cloud side ran Rancher across forty clusters, Loki for logs and Grafana Cloud for fleet dashboards. Connectivity used WireGuard; secrets came from Vault with local caching. A new store’s NUC was imaged with a prebuilt K3s installer including identity and GitOps config—plug in, and within about fifteen minutes the cluster was syncing from Git with no on-site DevOps.

Where this is heading

  • eBPF — Cilium works well as a CNI on constrained devices.
  • WebAssembly — smaller than containers, faster startup; projects like SpinKube bring WASM into Kubernetes.
  • AI at the edge — ML inference close to data sources is becoming routine.
  • Fleet tooling — Rancher Prime, Portainer Edge and peers compete on managing thousands of distant clusters.

The quiet revolution of orchestration everywhere

Not long ago, modern operations lived in the cloud and everything else was legacy. Edge computing changes that story. The same tools, patterns and deployment workflows now reach petrol pumps, retail stores, factory floors and hospital wards. For teams that already know Kubernetes, the unlock is large: open-source tools, a manageable learning curve, and a simpler way to run software across many locations. If any workload still needs a physical visit to update, take this seriously. Start small—one site, install K3s, deploy one workload. The pattern scales from there.
